# MASA (Mobile Application Security Assistant) — Tech Stack Recommendation

Confirmed for reference: Odysseus (PewDiePie's project) runs on **Python 3.11, FastAPI, SQLite, ChromaDB, and Docker**, connecting out to Ollama/llama.cpp/vLLM locally or OpenAI/OpenRouter as opt-in cloud fallback, under AGPL-3.0. That's a good validation of the direction already in the PRD — the recommendation below follows the same philosophy (boring, proven, local-first) but is adapted to MASA's actual workload: binary/bytecode analysis, not just chat.

**Standing principle, effective this revision: prefer an existing, maintained library over custom-built logic wherever one covers the need**, license permitting anything (the project ships MIT, so GPL/LGPL-licensed tools such as Semgrep and ldid must always be invoked as subprocesses, never imported as libraries). This revision replaces several "build from scratch" tasks from the original tasks list — custom regex/entropy secret scanning, a hand-written LLM client abstraction, custom RAG chunking, and a hand-maintained MASVS/MASTG mapping table — with existing tools that already solve those problems, several of which (Gitleaks, Semgrep) are already the established choice for this exact problem space in tools like MobSF.

## Recommended stack

| Layer | Choice | Why |
|---|---|---|
| Backend framework | **Python 3.11 + FastAPI** | Same as Odysseus. Also the path of least resistance for security tooling — androguard, LIEF, and most binary-analysis libraries are Python-native or have Python bindings. |
| Job queue | **RQ + Redis** (not Celery) | Scans are long-running (decompile + embed can take minutes). RQ is a fraction of Celery's operational complexity — one Redis container, one worker process. Celery is built for distributed multi-node systems; that's more than a single-user local tool needs. |
| Metadata storage | **SQLite** | Same as Odysseus. Zero-config, file-based, exactly right for a single-user local install. Upgrading to Postgres is a real option later if multi-user ever becomes a goal — not needed now. |
| Vector store | **ChromaDB, embedded mode** | Same as Odysseus. Runs in-process against a local file, no separate server/container to manage. |
| Android decompilation | **jadx** (Java/Kotlin source) + **androguard** (pure-Python manifest/permission/cert parsing) | jadx needs a JVM in the container (~200MB image cost, not a blocker). androguard covers a lot of manifest/permission work without needing the JVM at all, so it's worth using directly rather than shelling out to apktool for everything. |
| iOS static analysis | **LIEF** (Python bindings), not otool/class-dump | **This is a correction from the original PRD wording ("otool or equivalent").** otool and class-dump are macOS-only binaries — they will not run in a Linux Docker container, which breaks the "single Docker install" requirement outright. LIEF is a cross-platform C++/Python library that parses Mach-O binaries directly and runs fine on Linux. This swap is what makes iOS static analysis actually shippable in your stated deployment model. |
| iOS entitlements | Read the embedded code-signature blob via LIEF | `codesign -d --entitlements` is also macOS-only. Entitlements can be read directly from the Mach-O `__TEXT,__entitlements`/signature blob without shelling to `codesign` — but be upfront in the UI/docs that reliable extraction this way mostly works for ad-hoc-signed or resigned IPAs; some App Store-signed binaries encode entitlements in ways that are harder to recover without Apple's toolchain. Don't promise 100% coverage. |
| Edit & recompile (Android) | **Smali as the editable/recompilable layer**, via apktool. jadx's Java output stays read-only. | This is the load-bearing feasibility distinction for the whole feature. jadx produces readable Java for humans (and the agent) to reason about, but it is a one-way decompiler — there is no reliable path from edited jadx-Java back into working bytecode. apktool disassembles to **smali** (a readable intermediate representation of Dalvik bytecode) and can *reassemble* smali + resources back into an APK. So: agent/human read and reason in Java (clearer), but any change that needs to actually take effect gets expressed and applied as a smali edit, then apktool rebuilds. Resource/manifest/XML files (strings.xml, AndroidManifest.xml, network config) don't need this detour — apktool can edit and rebuild those directly. |
| Recompiled APK signing | Auto-generated local debug/test keystore via `keytool`, then `apksigner` + `zipalign` (Android SDK build-tools) | The original developer's signing key is never available, so a rebuilt APK can only be signed with a new, locally generated key. This must be surfaced clearly in the UI as a resigned test build — it will not match the original app's signature, cannot be pushed as an update to the original install, and isn't meant for distribution. This is standard practice in the mobile pentest community (the same approach tools like apktool/objection use), not a novel risk. |
| Edit & recompile (iOS) | **Resource/plist/entitlement edits only**, resigned ad-hoc via `ldid` | This is intentionally much narrower than Android. There is no smali-equivalent editable intermediate for compiled Objective-C/Swift — decompiled Mach-O pseudocode (from LIEF/a disassembler) isn't accurate or complete enough to safely round-trip back into working machine code without Xcode and the original project. Recompiling actual iOS *logic* changes is out of scope; that class of testing (e.g. bypassing a pinning check at runtime) belongs to dynamic instrumentation (Frida), which is already an explicit v1 non-goal. iOS recompile in v1 should only cover things that don't require touching compiled code: Info.plist tweaks, entitlement changes, resource swaps, then resigning for sideload testing. |
| Secrets/string scanning | **Gitleaks** (subprocess-wrapped), not a custom regex/entropy scanner | Gitleaks is a maintained, fast (Go binary), actively-updated secret detector with a large ruleset covering hundreds of API key/token formats plus entropy-based fallback detection — exactly what the "regex + entropy scanner" task was reinventing, and better maintained than anything built in-house would be day one. Runs the same way against Android decompiled output and iOS binary/resource strings, so it's shared across M1 and M2 as originally planned — just via a real tool instead of custom code. MIT license. |
| Code-level security pattern findings | **Semgrep**, using community + OWASP-oriented Java/Kotlin rulesets | Manifest-level findings (permissions, exported components) already come from androguard, but *code-level* patterns — insecure WebView config, weak crypto usage, hardcoded trust managers, and similar — are exactly the kind of structural pattern-matching Semgrep exists for, rather than something to hand-write finding-by-finding. Notably, this is the same tool MobSF itself has adopted for parts of its Java/Kotlin analysis in recent versions — reusing it here isn't a novel choice, it's already the established approach in this exact problem space. License note: Semgrep's CLI has shifted licensing over versions (LGPL-2.1 in places). It is invoked strictly as a subprocess (never imported as a library), which keeps it compatible with MASA's MIT license — still worth pinning a specific version and license-checking at implementation time. |
| Frontend | **React + Vite + Tailwind** | Lighter than Next.js — no SSR or routing complexity needed for a single local dashboard. Vite gives fast local dev. The existing mockup's design tokens (colors, IBM Plex fonts, spacing) translate directly into a Tailwind config, so the visual design carries over rather than being redone. |
| Real-time scan status | **Polling** (not WebSockets) | A 2-3 second poll interval is invisible to a human watching a progress bar. WebSockets add real complexity (connection lifecycle, reconnect handling) for no user-visible benefit at this scale. Revisit only if usage patterns actually demand push updates. |
| LLM connectivity | MASA's own container **does not bundle an LLM** — it connects outward to Ollama/LM Studio running on the host, via **LiteLLM** as the client library rather than a hand-written client class | Containerizing GPU-backed model serving (Docker + NVIDIA runtime + driver matching) is a well-known source of pain and would make "single `docker-compose up`" a broken promise for most users. Ollama/LM Studio already solve local model serving well on the host; MASA should just be a good client of them. LiteLLM specifically replaces the custom "LLM client class" and "BYOK provider abstraction" tasks — it already normalizes Ollama, LM Studio (OpenAI-compatible), OpenAI, Anthropic, Gemini, DeepSeek, Mistral, Groq, xAI, and OpenRouter behind one interface, including consistent function/tool-calling schemas across providers where each provider supports them. Writing that abstraction from scratch means re-solving a problem LiteLLM already solves and maintains against provider API drift. MIT license. |
| Deployment | Docker Compose, 3 services: **app** (FastAPI + RQ worker) + **redis** + **searxng** | SQLite and Chroma are both file-based/embedded, so they don't need their own containers. SearXNG does need its own container (it's a proxy service, not embeddable) — it's the one addition to the "boring, minimal compose file" goal, and it's the same addition Odysseus itself makes for the same reason. |
| Agent tool-calling | LiteLLM's normalized function-calling interface, still restricted to a **documented "known-good" model list** (Qwen2.5/2.5-coder, Llama 3.1+) | LiteLLM removes the need to hand-write provider-specific tool-call parsing, but it doesn't remove the underlying limitation: not every local model reliably *follows* structured tool-call output even when the API supports the format — that's a model capability gap, not a client-library problem, and no library fixes it. Ship a short list of verified-compatible models and fail gracefully (fall back to plain RAG chat without tools) for anything else. |
| RAG chunking | **LlamaIndex's `CodeSplitter`** (tree-sitter based) instead of a hand-rolled chunking strategy | The M4 task "chunking strategy for decompiled source (per-class or per-method — test both)" is exactly what tree-sitter-aware code splitters are built for — they parse actual syntax boundaries instead of naive line/character splitting, so chunks reliably align with method/class boundaries. Saves the trial-and-error that task implied, and handles both Java (Android) and reasonably well for other source-like text. Apache 2.0 license, works fine as a library dependency alongside ChromaDB. |
| MASVS/MASTG mapping data | Sourced from the **official OWASP MASTG repository's mapping files**, not a hand-maintained lookup table | OWASP publishes structured mapping data (MASTG test IDs, MASVS control IDs) as part of the MASTG repo itself. Pulling from that directly (vendored at build time or fetched/cached) means the mapping stays current with the actual standard as OWASP updates it, instead of drifting from a copy someone typed in once. |
| Deep research pipeline | Adapt from **GPT Researcher** (open-source reference implementation) rather than building the search→fetch→summarize→synthesize flow from scratch, pointed at self-hosted SearXNG as its retriever | GPT Researcher already implements the multi-step research pattern (query → multiple source fetch → per-source summarization → synthesis with citations) that the M7 task describes building. It supports pluggable retrievers, so it can be configured against SearXNG instead of its default web search, keeping the local-first search choice while reusing a maintained pipeline instead of writing one. Apache 2.0 license. Still worth keeping the pipeline **bounded** (fixed source count) as originally planned, rather than adopting its full autonomous-research feature set on day one. |
| Web research / deep research | **Self-hosted SearXNG** (its own container) as the default search provider, with a pluggable fallback chain (Brave, DuckDuckGo, Tavily, Serper, Google PSE) via API keys, following Odysseus's exact pattern | SearXNG is a metasearch proxy — it aggregates results from public engines without you needing an API key, and keeps the "no per-query API cost" property that fits an open-source tool. It does mean queries still leave the machine (SearXNG proxies out to the public internet), so this should be clearly separated from the local-only guarantee in the UI, not blended into it. |
| License | **MIT** | Revised from the original AGPL-3.0 decision: MIT maximizes adoption and self-hosting for a single-user tool. The GPL/LGPL-licensed tools in the stack (Semgrep, ldid) are invoked strictly as subprocesses, never imported, which keeps the MIT license clean. |

## Explicit feasibility corrections from the original PRD

1. **iOS static analysis via otool/class-dump was not actually feasible** in a Linux Docker container — those tools require macOS. Fixed by switching to LIEF. This was worth catching now rather than discovering it mid-M2.
2. **Entitlement extraction has a real coverage ceiling** without Apple's signing toolchain — the PRD should say "best-effort entitlement extraction for ad-hoc/resigned IPAs" rather than implying full parity with a macOS-based tool.
3. **Tool-calling reliability is model-dependent**, not something MASA's code can guarantee universally. Scope it to a known-good model list rather than an open-ended "the agent calls tools" claim.
4. **GPU/Docker passthrough is not required** for MASA itself, because the LLM runs on the host via Ollama/LM Studio, not inside MASA's own container — this keeps "single Docker install" a promise you can actually keep.
5. **Web research is not the same privacy boundary as local inference** — SearXNG queries still leave the machine even though it's self-hosted and API-key-free. The UI needs to be honest about that distinction rather than letting "local-only" branding bleed into a feature that inherently talks to the public internet.
6. **"Recompile" only works through smali, not through the Java view.** jadx's decompiled Java is one-way — there's no supported path back to working bytecode from edited Java source. The UI has to make this distinction visible (a Java/Smali toggle, with edits only enabled in Smali) rather than implying any visible code is directly editable-and-rebuildable. iOS recompiling is scoped even narrower — resources/plist/entitlements only, since there's no smali-equivalent intermediate for compiled Swift/Objective-C without Xcode and the original project.

None of these change the product's scope or ambition — they change *how* a couple of features get built so the stated deployment model (single Docker Compose, cross-platform, local-first) stays true rather than becoming aspirational.
