# MASA (Mobile Application Security Assistant) — Tech Stack Recommendation

Confirmed for reference: Odysseus (PewDiePie's project) runs on **Python 3.11, FastAPI, SQLite, ChromaDB, and Docker**, connecting out to Ollama/llama.cpp/vLLM locally or OpenAI/OpenRouter as opt-in cloud fallback, under AGPL-3.0. That's a good validation of the direction already in the PRD — the recommendation below follows the same philosophy (boring, proven, local-first) but is adapted to MASA's actual workload: binary/bytecode analysis, not just chat.

**Standing principle, effective this revision: prefer an existing, maintained library over custom-built logic wherever one covers the need**, license permitting anything (the project ships Apache-2.0, so GPL/LGPL-licensed tools such as Semgrep and ldid must always be invoked as subprocesses, never imported as libraries). This revision replaces several "build from scratch" tasks from the original tasks list — custom regex/entropy secret scanning, a hand-written LLM client abstraction, and a hand-maintained MASVS/MASTG mapping table — with existing tools that already solve those problems, several of which (Gitleaks, Semgrep) are already the established choice for this exact problem space in tools like MobSF.

**Owner decision (Aug 6, 2026): the M4 RAG/embedding pipeline (ChromaDB +
LlamaIndex CodeSplitter + LiteLLM embeddings) was deleted from v1, not
deferred** — CPU-only embedding of a 3MB APK took 5-15 minutes before chat was
even usable. The agent layer is non-embedding: **Layer 1** full findings
context (precision-tagged), **Layer 2** `search_code`/`read_file` tools,
**Layer 3** Graphify graph tools (Android). No vector store exists in the
stack.

## Recommended stack

| Layer | Choice | Why |
|---|---|---|
| Backend framework | **Python 3.11 + FastAPI** | Same as Odysseus. Also the path of least resistance for security tooling — androguard, LIEF, and most binary-analysis libraries are Python-native or have Python bindings. |
| Job queue | **RQ + Redis** (not Celery) | Scans are long-running (decompile can take minutes; graph build too). RQ is a fraction of Celery's operational complexity — one Redis container, one worker process. Celery is built for distributed multi-node systems; that's more than a single-user local tool needs. |
| Metadata storage | **SQLite** | Same as Odysseus. Zero-config, file-based, exactly right for a single-user local install. Upgrading to Postgres is a real option later if multi-user ever becomes a goal — not needed now. |
| Vector store | **None — no embeddings in v1** | **Owner decision (Aug 6): the ChromaDB + embeddings pipeline was deleted from v1.** The agent layer is non-embedding: Layer 1 = full findings context (data lookup), Layer 2 = `search_code`/`read_file` over the decompiled tree, Layer 3 = Graphify graph traversal. Nothing to run, nothing to manage. |
| Android decompilation | **jadx** (Java/Kotlin source) + **androguard** (pure-Python manifest/permission/cert parsing) | jadx needs a JVM in the container (~200MB image cost, not a blocker). androguard covers a lot of manifest/permission work without needing the JVM at all, so it's worth using directly rather than shelling out to apktool for everything. |
| iOS static analysis | **LIEF** (Python bindings), not otool/class-dump | **This is a correction from the original PRD wording ("otool or equivalent").** otool and class-dump are macOS-only binaries — they will not run in a Linux Docker container, which breaks the "single Docker install" requirement outright. LIEF is a cross-platform C++/Python library that parses Mach-O binaries directly and runs fine on Linux. This swap is what makes iOS static analysis actually shippable in your stated deployment model. |
| iOS entitlements | Read the embedded code-signature blob via LIEF | `codesign -d --entitlements` is also macOS-only. Entitlements can be read directly from the Mach-O `__TEXT,__entitlements`/signature blob without shelling to `codesign` — but be upfront in the UI/docs that reliable extraction this way mostly works for ad-hoc-signed or resigned IPAs; some App Store-signed binaries encode entitlements in ways that are harder to recover without Apple's toolchain. Don't promise 100% coverage. |
| Edit & recompile (Android) | **Smali as the editable/recompilable layer**, via apktool. jadx's Java output stays read-only. | This is the load-bearing feasibility distinction for the whole feature. jadx produces readable Java for humans (and the agent) to reason about, but it is a one-way decompiler — there is no reliable path from edited jadx-Java back into working bytecode. apktool disassembles to **smali** (a readable intermediate representation of Dalvik bytecode) and can *reassemble* smali + resources back into an APK. So: agent/human read and reason in Java (clearer), but any change that needs to actually take effect gets expressed and applied as a smali edit, then apktool rebuilds. Resource/manifest/XML files (strings.xml, AndroidManifest.xml, network config) don't need this detour — apktool can edit and rebuild those directly. |
| Recompiled APK signing | Auto-generated local debug/test keystore via `keytool`, then `apksigner` + `zipalign` (Android SDK build-tools) | The original developer's signing key is never available, so a rebuilt APK can only be signed with a new, locally generated key. This must be surfaced clearly in the UI as a resigned test build — it will not match the original app's signature, cannot be pushed as an update to the original install, and isn't meant for distribution. This is standard practice in the mobile pentest community (the same approach tools like apktool/objection use), not a novel risk. |
| Edit & recompile (iOS) | **Resource/plist/entitlement edits only**, resigned ad-hoc via `ldid` — **deferred to v1.1** (owner decision, Aug 10, 2026: not shipped in v1/M8) | This is intentionally much narrower than Android. There is no smali-equivalent editable intermediate for compiled Objective-C/Swift — decompiled Mach-O pseudocode (from LIEF/a disassembler) isn't accurate or complete enough to safely round-trip back into working machine code without Xcode and the original project. Recompiling actual iOS *logic* changes is out of scope; that class of testing (e.g. bypassing a pinning check at runtime) belongs to dynamic instrumentation (Frida), which is already an explicit v1 non-goal. iOS recompile (when it lands in v1.1) should only cover things that don't require touching compiled code: Info.plist tweaks, entitlement changes, resource swaps, then resigning for sideload testing. **Deferred to v1.1 at the M8 kickoff (Aug 10, 2026)** — the path above stays the v1.1 target; v1 ships Android-only edit/recompile. |
| Secrets/string scanning | **Gitleaks** (subprocess-wrapped), not a custom regex/entropy scanner | Gitleaks is a maintained, fast (Go binary), actively-updated secret detector with a large ruleset covering hundreds of API key/token formats plus entropy-based fallback detection — exactly what the "regex + entropy scanner" task was reinventing, and better maintained than anything built in-house would be day one. Runs the same way against Android decompiled output and iOS binary/resource strings, so it's shared across M1 and M2 as originally planned — just via a real tool instead of custom code. MIT license. |
| Code-level security pattern findings | **Semgrep**, using community + OWASP-oriented Java/Kotlin rulesets | Manifest-level findings (permissions, exported components) already come from androguard, but *code-level* patterns — insecure WebView config, weak crypto usage, hardcoded trust managers, and similar — are exactly the kind of structural pattern-matching Semgrep exists for, rather than something to hand-write finding-by-finding. Notably, this is the same tool MobSF itself has adopted for parts of its Java/Kotlin analysis in recent versions — reusing it here isn't a novel choice, it's already the established approach in this exact problem space. License note: Semgrep's CLI has shifted licensing over versions (LGPL-2.1 in places). It is invoked strictly as a subprocess (never imported as a library), which keeps it compatible with MASA's Apache-2.0 license — still worth pinning a specific version and license-checking at implementation time. |
| Frontend | **React + Vite + Tailwind** | Lighter than Next.js — no SSR or routing complexity needed for a single local dashboard. Vite gives fast local dev. The existing mockup's design tokens (colors, IBM Plex fonts, spacing) translate directly into a Tailwind config, so the visual design carries over rather than being redone. |
| Real-time scan status | **Polling** (not WebSockets) | A 2-3 second poll interval is invisible to a human watching a progress bar. WebSockets add real complexity (connection lifecycle, reconnect handling) for no user-visible benefit at this scale. Revisit only if usage patterns actually demand push updates. |
| LLM connectivity | MASA's own container **does not bundle an LLM** — it connects outward to Ollama/LM Studio running on the host, via **LiteLLM** as the client library rather than a hand-written client class | Containerizing GPU-backed model serving (Docker + NVIDIA runtime + driver matching) is a well-known source of pain and would make "single `docker-compose up`" a broken promise for most users. Ollama/LM Studio already solve local model serving well on the host; MASA should just be a good client of them. LiteLLM specifically replaces the custom "LLM client class" and "BYOK provider abstraction" tasks — it already normalizes Ollama, LM Studio (OpenAI-compatible), OpenAI, Anthropic, Gemini, DeepSeek, Mistral, Groq, xAI, and OpenRouter behind one interface, including consistent function/tool-calling schemas across providers where each provider supports them. Writing that abstraction from scratch means re-solving a problem LiteLLM already solves and maintains against provider API drift. MIT license. |
| Deployment | Docker Compose: **app** (FastAPI + RQ worker) + **redis** always-on; **searxng** under `profiles: [web]` (M7) | SQLite is file-based and the (former) Chroma store was embedded, so neither needs its own container. SearXNG needs its own container (a proxy service, not embeddable) — the same addition Odysseus makes — but it's **profile-gated** (owner decision, Aug 9) so the default `docker compose up` runs only app+redis; the user starts it when the SearXNG engine is Active in Settings (`docker compose --profile web up -d searxng`). |
| Agent tool-calling | LiteLLM's normalized function-calling interface; the **known-good model list (Qwen2.5/2.5-coder, Llama 3.1+) is a documented RECOMMENDATION, not a hard gate** — tools are offered to any configured model (M6 owner decision, Aug 8: soft offer). M6 adds the app-oriented tool set (`read_manifest`, `get_decompiled_class` Android-only, `get_permissions`, `run_secrets_scan` on-demand gitleaks re-run, `search_strings`) to the M4 Layers 2/3 set, with per-scan platform filtering of tool schemas. | LiteLLM removes the need to hand-write provider-specific tool-call parsing, but it doesn't remove the underlying limitation: not every local model reliably *follows* structured tool-call output even when the API supports the format — that's a model capability gap, not a client-library problem, and no library fixes it. The known-good list is documented in `docs/progress/M6.md`; the safety net stays the existing runtime fallbacks — `agent/chat.py` answers context-only (Layers 1-3, no tools) when the model emits no tool calls, and degrades to plain chat when a backend rejects the `tools` kwarg. `tool_mode: tools \| context-only` on the chat response tells the UI which path ran. |
| Agent context (was "RAG chunking") | **No chunking, no embeddings** — Layer 1 is the full findings set from the unified `findings` table, rendered precision-tagged; Layer 2 greps/reads the decompiled tree directly | **Owner decision (Aug 6): removed with the RAG pipeline.** Embeddings per scan took 5-15 min on CPU for a 3MB APK and bought fuzzy semantic recall that Layers 1-3 answer deterministically and faster: every static finding (all sources), grep with file/line, file reads, and Graphify graph traversal. The one lost capability — imprecise open-ended recall ("which parts touch X" when you don't know an identifier or finding) — was judged not worth the indexing cost. |
| MASVS/MASTG mapping data | Sourced from the **official OWASP MASTG repository's mapping files**, not a hand-maintained lookup table | OWASP publishes structured mapping data (MASTG test IDs, MASVS control IDs) as part of the MASTG repo itself. Pulling from that directly (vendored at build time or fetched/cached) means the mapping stays current with the actual standard as OWASP updates it, instead of drifting from a copy someone typed in once. |
| Agent web research (M7) | **On-demand `web_search` + `web_fetch` agent tools** in the existing M4/M6 tool loop, gated by a **two-layer model** — per-scan opt-in (the dock 🌐 toggle, an engine-agnostic privacy gate: may this scan's agent leave the machine at all? — **disabled until an engine is Active**) AND an **Active engine configured in Settings** (which engine — SearXNG today, Brave/Serper later) — not a standalone deep-research pipeline (owner reframe, Aug 9: *"isn't it just when the AI doesn't have the answer we trigger a search, like Gemini/ChatGPT?"*) | The model decides when a question needs current/external info (CVE lookups, MASTG guidance, dependency versions) and calls `web_search`; `web_fetch` reads the top pages (httpx + **trafilatura ≥1.8.0** extraction, Apache-2.0 — earlier trafilatura versions were GPLv3+, hence the pin). The originally-planned **GPT Researcher / deep-research pipeline was dropped** at kickoff (its Apache-2.0 license was verified, so this is a scope decision, not a license one — the bounded pattern is simple enough to own). No browser in v1: static pages (advisories, MASTG MkDocs docs) read fine via fetch; JS-rendered pages degrade. |
| Web search (M7) | **Self-hosted SearXNG** as the bundled search provider (its own container, **profile-gated** so the default `docker compose up` stays lean), plus a **provider registry + JSON store mirroring the M3/M5 BYOK pattern** — v1 implements SearXNG only, with **custom SearXNG-compatible instances** (base URL, no key) as the free-form analogue to BYOK custom endpoints; Brave / Serper / Mojeek are later registry rows + small normalizers. **Each backend carries an Active/Inactive toggle in Settings, one Active at a time** (radio — enabling one disables the others; owner decision Aug 9, mirroring `pick_chat_backend` determinism); the store keeps `enabled` + `order` so a priority fallback chain is a resolver-only change later | SearXNG is a metasearch proxy — it aggregates results from public engines without an API key, keeping the "no per-query API cost" property. It is **AGPL-3.0**, but MASA stays clean because the boundary is structural: unmodified upstream image, separate container, HTTP JSON API only — never imported/vendored/forked (AGPL §13 reaches modified copies of SearXNG itself, not separate programs that call it; see `docs/licenses.md`). Queries still leave the machine (SearXNG proxies to the public internet) — clearly separated from the local inference guarantee in the UI. Future-provider feasibility: Brave (official REST API, ~$5/mo credit), Serper (official, trial credits), Mojeek (official, free trial) are viable; Google CSE (closing to new customers Jan 2027), Bing v7 (dead — HTTP 410), and DuckDuckGo (no official API — scraping only, ToS-grey) are ruled out. |
| Interactive browser automation | **DROPPED from v1** (owner decision, Aug 9, 2026) — vercel-labs `agent-browser` is not shipped | The original M7 plan paired SearXNG (find) with agent-browser (drive/read JS-rendered pages via CDP Chrome). At kickoff the owner cut browser automation entirely: M7 is on-demand search + static-page fetch only. JS-rendered page verification (clicking through interactive advisories) is deferred until a future browser capability is explicitly wanted; MASTG docs and most security advisories are static HTML and read fine via `web_fetch`. |
| License | **Apache-2.0** | Revised from the original AGPL-3.0 decision: Apache-2.0 maximizes adoption and self-hosting for a single-user tool. Copyleft stays behind process boundaries: the GPL/LGPL tools (Semgrep, ldid) are invoked strictly as subprocesses, never imported; **SearXNG (AGPL-3.0) runs as an unmodified, separate container reached only over its HTTP JSON API** — never vendored, pip-installed, or forked, so AGPL §13 never reaches MASA. All imported libraries are permissive (see `docs/licenses.md`). | | Code structure understanding | **Graphify** (`graphifyy` on PyPI), code-only extraction mode — **M4 Layer 3** | Builds a deterministic call/import/inheritance graph from decompiled Java via tree-sitter AST — no LLM, no API key, fully local for code. Layer 3 of the non-embedding agent stack: graph traversal answers structural questions ("where is X," "what calls Y") more precisely than grep/findings context alone; Layer 1 findings + Layer 2 search/read cover the rest. Apache-2.0/MIT dual-licensed — clean fit for MIT, no subprocess-boundary reasoning even required (though invoke it as a subprocess anyway, consistent with how the other CLI tools are used). Scope usage narrowly to the headless `update <dir> --no-cluster` build and `query`/`path`/`explain`/`affected` — the tool's full surface area (PR triage, video/PDF ingestion, Neo4j/Obsidian export) is out of scope for MASA. iOS is **confirmed negative** (Aug 6): an unpacked `.app` has no source-like files, so Graphify is Android-only in v1. |

## Explicit feasibility corrections from the original PRD

1. **iOS static analysis via otool/class-dump was not actually feasible** in a Linux Docker container — those tools require macOS. Fixed by switching to LIEF. This was worth catching now rather than discovering it mid-M2.
2. **Entitlement extraction has a real coverage ceiling** without Apple's signing toolchain — the PRD should say "best-effort entitlement extraction for ad-hoc/resigned IPAs" rather than implying full parity with a macOS-based tool.
3. **Tool-calling reliability is model-dependent**, not something MASA's code can guarantee universally. Scope it to a known-good model list rather than an open-ended "the agent calls tools" claim.
4. **GPU/Docker passthrough is not required** for MASA itself, because the LLM runs on the host via Ollama/LM Studio, not inside MASA's own container — this keeps "single Docker install" a promise you can actually keep.
5. **Web research is not the same privacy boundary as local inference** — SearXNG queries still leave the machine even though it's self-hosted and API-key-free. The UI needs to be honest about that distinction rather than letting "local-only" branding bleed into a feature that inherently talks to the public internet.
6. **"Recompile" only works through smali, not through the Java view.** jadx's decompiled Java is one-way — there's no supported path back to working bytecode from edited Java source. The UI has to make this distinction visible (a Java/Smali toggle, with edits only enabled in Smali) rather than implying any visible code is directly editable-and-rebuildable. iOS recompiling is scoped even narrower — resources/plist/entitlements only, since there's no smali-equivalent intermediate for compiled Swift/Objective-C without Xcode and the original project (and that iOS path is itself deferred to v1.1 — owner decision, Aug 10, 2026).
8. **Graphify is Layer 3 of a non-embedding agent stack, not a RAG sidekick.** After
   the RAG/embedding removal (owner decision, Aug 6), Graphify's code graph is the
   structural layer: it builds a deterministic call graph from decompiled Android
   source with zero LLM cost, directly answering "where is certificate pinning
   located"-class questions — Layer 1 findings context and Layer 2 search/read tools
   cover the rest. **iOS is confirmed negative** (tree-sitter expects real source
   syntax; an unpacked `.app` has zero source-like files), so it is Android-only in
   v1, and it is used narrowly (headless build + query/path/explain only), not for
   its full feature surface.
9. **`web_fetch` is the M7 fetch path — agent-browser was dropped at kickoff.**
   The original plan paired SearXNG with vercel-labs `agent-browser` (CDP
   Chrome) for reading/clicking JS-rendered pages. The owner cut browser
   automation entirely (Aug 9): M7's fetch step is a hand-rolled
   `web_fetch(url)` over httpx + **trafilatura ≥1.8.0** extraction (Apache-2.0
   at that pin; earlier versions GPLv3+), bounded to agent-friendly article
   text. Static pages (advisories, MASTG MkDocs docs) read fine; JS-rendered
   pages degrade to their static content — acceptable in v1.

None of these change the product's scope or ambition — they change *how* a couple of features get built so the stated deployment model (single Docker Compose, cross-platform, local-first) stays true rather than becoming aspirational.
