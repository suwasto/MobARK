## Build notes (Aug 9, 2026)

All five app-oriented tools shipped in `agent/tools.py` alongside the
existing Layers 2/3 set; every one is bounded (tool-level caps), reuses the
existing wrappers (`resolve_tree_root`, plistlib/`load_info_plist`,
`analysis/gitleaks.py::scan_directory`, `analysis/manifest.py`
`RISKY_PERMISSIONS`) and never invokes a raw subprocess from the agent layer:

- **`read_manifest()`** — Android parses the decompiled
  `resources/AndroidManifest.xml` with stdlib ElementTree (jadx emits
  readable XML; the helper is defensive about the no-`sources/` layout);
  iOS reads the bundle `Info.plist` via `load_info_plist` (binary + XML).
  JSON, capped at `_MAX_MANIFEST_CHARS` (list fields shrink, never a
  truncated string).
- **`get_decompiled_class(fqcn)`** — Android only: `com.app.Foo` →
  `sources/com/app/Foo.java` (`.kt` fallback; `$` inner classes work),
  capped at `_MAX_CLASS_CHARS`; invalid names and missing classes are clean
  `ToolError`s; iOS gets the explicit "no decompiled source" error (the
  Phase B schema filter makes the model never see it in the first place).
- **`get_permissions()`** — Android: every `<uses-permission>` with
  `maxSdkVersion` + a `dangerous` flag derived from the app's curated
  `RISKY_PERMISSIONS` set (documented as curated, not the full SDK
  database); iOS: usage-description keys (key + human label + value).
- **`run_secrets_scan(path)`** — on-demand re-run wrapping
  `scan_directory` with a 30 s per-call timeout, a size/file-count guard
  (`_SECRETS_SCAN_MAX_MB`/`_MAX_FILES`), and traversal guard; results
  normalized to `{rule_id, file, line, severity, description}`, capped at
  50. Layer 1 already carries the persisted secrets scan — this tool is for
  re-checking a narrower path.
- **`search_strings(pattern)`** — `search_code` over a resource/string glob
  set (`**/*.xml`, `**/*.strings`, `**/*.json`, `**/*.properties`,
  `**/*.txt`), deduped, same result shape as `search_code`.

Phase B: `schemas_for_platform()` filters `TOOL_SCHEMAS` per scan platform
(iOS never sees `get_decompiled_class` — the `_ANDROID_ONLY_TOOLS` set,
same whitelist pattern as `context.py::platform_tools`); `ChatResponse`
gained `tool_mode: "tools" | "context-only"` + `tools_used`, and the Agent
dock renders a small "tools used" line. Phase C: `max_tool_rounds` is a
settings knob (`MASA_MAX_TOOL_ROUNDS`, default 3) with a per-request
override on `ChatRequest`; the new tools carry per-call timeout/size guards.

Gates: **339 backend tests green (+27 for M6) + ruff clean; `tsc -b` +
`vite build` green.** Containerized e2e + real-model QA remain owner
checkpoints (Ollama off during dev; the chat contract shape — 400/502/504,
tool schemas in the request — is unchanged except the additive fields).

## Follow-up (Aug 9, 2026 — live tool steps + token streaming in the dock)

Owner brainstorm → build: the dock now shows the agent working, mainstream-
AI style, over a new SSE endpoint `POST /scans/{id}/chat/stream` (the
buffered `/chat` stays for the CLI/tests):

- **Backend.** `model/client.py::chat_stream` (litellm `stream=True`, every
  provider normalized to the OpenAI chunk shape); `agent/chat.py::answer_question`
  gains `stream` + `on_event` — content deltas forward as `token` events and
  each executed call emits `tool_start`/`tool_end` around it, with a
  `ToolRun` recorded for the persistent `tool_runs` trace on `AgentResult` /
  `ChatResponse`. Tool-call deltas accumulate defensively (missing index →
  call id → position; `arguments` concatenated per index). The
  tools-kwarg-rejected fallback and the loop-exhaustion plain chat both
  stream too. Frames: `token` · `tool_start` · `tool_end` · `answer`
  (canonical payload incl. `tool_runs`) · `error` (kind+detail). Pre-stream
  HTTP: 400 no-model (explicit `check_configured` guard), 409 not-analyzed,
  404 unknown scan. The route runs `answer_question` on a worker thread
  pushing frames through a queue (live yields), with 15 s keepalive comments
  during long tool calls; the existing cancel machinery stops the loop at the
  next boundary.
- **Frontend.** `lib/sse.ts` incremental `StreamDecoder`; `api.chatStream()`
  raw-fetch path; `useChat` reworked around a ref-backed pending turn (token
  buffer flushed every 50 ms; abort keeps partial text + steps and the dock
  appends the existing "Stopped" note). The dock renders streaming text with
  a blinking caret, live step rows (pulsing running state → ✓/✗ + duration +
  result count), expandable args/result per step with clickable file:line
  chips reusing `openInDecompiler`, and after the turn a collapsed `Tools
  (n)` trace — replacing the M6 one-line tools-row. Context-only turns show a
  subtle "answered from findings context" tag.
- **Tests (mocked, no Ollama).** 11 new: stream token/answer, cross-chunk
  tool-call accumulation, tool error status, missing-index deltas,
  tools-rejection fallback streams too, cancel between rounds; route-level
  ordered SSE frames, error-frame kinds (upstream/timeout/interrupted/
  no-model), pre-stream 400, 409/404, timeout+max_tool_rounds forwarding.
  Route tests patch `check_configured` for hermeticity (no real store).
- **Gates: 350 backend tests green (+11) + ruff clean; `tsc -b` + `vite

flagship test cases** that prove the loop is genuinely useful.

## Owner decisions (locked Aug 8, 2026)

1. **`run_secrets_scan` = on-demand re-run** — wraps the existing gitleaks
   wrapper (`analysis/gitleaks.py::scan_directory`) over a targeted
   path/glob with a per-call timeout + size guard. Rationale: Layer 1
   context already carries every *persisted* gitleaks finding, so a
   "query what we scanned" tool would be redundant; the value is
   re-running over a targeted path (e.g. a resource dir the scan skipped).
2. **Model gating = soft offer** — tools are offered to ANY configured
   model; the existing runtime fallbacks (no tool calls emitted →
   context-only; `tools=` kwarg rejected → plain chat) handle unreliable
   models. The known-good list (Qwen2.5/2.5-coder, Llama 3.1+) is
   **documented as a recommendation** in the tech-stack doc, NOT a hard
   gate (owner overrode the initial "hard gate" recommendation).
3. **iOS scope = both platforms** — `read_manifest` maps to Info.plist on
   iOS; `get_permissions` returns usage-description keys; `get_decompiled_class`
   stays Android-only (no decompiled Swift/ObjC source exists in v1).

## Phase A — App-oriented tools (extend `agent/tools.py`, platform-aware)

All new tools follow the existing conventions: `ToolError` → `{"error":…}`
JSON result, bounded result sizes, no platform branching inside the tool
(only `resolve_tree_root` knows the platform).

| Tool | Platforms | Source of truth | Result |
|---|---|---|---|
| `read_manifest()` | android + ios | decompiled `AndroidManifest.xml` (resources root) / `Info.plist` (bundle, plistlib) | bounded JSON: package, min/target SDK, debuggable, allowBackup, cleartext, exported components / bundle id, version, ATS, usage strings, background modes |
| `get_decompiled_class(fqcn)` | android | jadx `sources/` tree (resolve `com.app.Foo` → `com/app/Foo.java`) | bounded source; clean missing-class error; iOS → explicit "no decompiled source on iOS" error |
| `get_permissions()` | android + ios | manifest uses-permission set / usage-description keys | name + `maxSdkVersion` + dangerous flag; iOS usage strings |
| `run_secrets_scan(glob)` | both | on-demand `gitleaks.py::scan_directory` | normalized findings, per-call timeout + size cap |
| `search_strings(pattern)` | both | `search_code` with `mode="strings"` (targets `strings.xml`/resources) | same shape as `search_code` |

**Reuse, don't reimplement:** manifest parsing reuses `analysis/manifest.py`
where possible; plist decoding reuses the existing `read_file` plist path;
gitleaks wraps the existing M1 wrapper (never a raw subprocess from the
agent layer).

## Phase B — Platform-aware schemas + soft-offer gating

- **Filter `TOOL_SCHEMAS` per scan by platform** (extend the `context.py`
  whitelist pattern) — iOS never *sees* Android-only tools (`get_decompiled_class`),
  so the model can't waste a round on a guaranteed-failing call.
- **Known-good list documented, tools offered to any model** (soft).
  `agent/chat.py` keeps both runtime fallbacks unchanged as the safety net.
- **Surface `tool_mode: tools | context-only`** (+ existing `tools_used`) in
  `ChatResponse` so the dock can show whether tools ran this turn.

## Phase C — Loop hardening

Existing bounds stay (≤3 rounds, 120 s deadline, per-tool result caps).
Additions:
- Per-call timeout/size guards on the four new tools (e.g. secrets scan
  capped at ~30 s and a bounded tree walk).
- Expose `max_tool_rounds` as a config knob (`settings`) — same pattern as
  the existing `chat_timeout_seconds`.
