## The reframe (owner, Aug 9, 2026)

The original M7 plan (written Aug 7) was **deep research + interactive browser
automation**: a GPT Researcher-style search→fetch→summarize→synthesize
pipeline plus vercel-labs `agent-browser` (CDP-driven Chrome) for reading and
clicking JS-rendered pages. At kickoff the owner cut both:

1. **`agent-browser` is DROPPED** — no browser automation in v1. No Chrome for
   Testing, no snapshot/click/fill tools, no deployment decision.
2. **The deep-research pipeline is DROPPED.** Owner's reframe (verbatim
   intent): *"do we really need deep research? isn't it just when the user
   asks something and the AI doesn't have the answer, we trigger a search —
   like Gemini/DeepSeek/ChatGPT?"* Correct — and it's simpler than what was
   planned: web research becomes **two on-demand agent tools**
   (`web_search`, `web_fetch`) in the existing M4/M6 tool-calling loop. The
   model decides when a question needs current/external info (CVE lookups,
   MASTG guidance, dependency versions) and calls the tools, exactly like
   mainstream AI web-search modes. No pipeline feature, no GPT Researcher
   dependency, no LangChain.

What survives from the original plan, re-scoped: **SearXNG as the search
provider** (profile-gated compose service), the **extendable provider
registry** (BYOK-style, SearXNG-only in v1), **per-scan opt-in**, and the
"leaves the machine" privacy boundary in the UI.

## Owner decisions (locked Aug 9, 2026)

1. **Agent-browser dropped outright** — static-page fetch only in v1; JS
   rendered pages degrade (acceptable — advisories + MASTG docs are static).
2. **Deep research / GPT Researcher dropped** — on-demand `web_search` +
   `web_fetch` agent tools instead. GPT Researcher was verified **Apache-2.0**
   (the tech-stack claim was correct), so dropping it is a scope decision,
   not a license one; the bounded pattern is simple enough to own (~200
   lines).
3. **SearXNG deployment = bundled, profile-gated** — a `searxng` compose
   service under `profiles: [web]`, started when the SearXNG engine is
   **Active** and web research is in use (`docker compose --profile web up
   -d searxng`); the default `docker compose up` stays lean. The Active
   toggle (decision 6) never auto-starts the container — it marks the
   configured engine; reachability is probed separately.
4. **Provider registry now, SearXNG only** — `search/providers.py` table +
   JSON store + one normalizer interface are built in M7, but the only
   implemented engine is SearXNG; users may also add **custom
   SearXNG-compatible instances** (base URL, no key) — the free-form analogue
   to BYOK custom endpoints. Brave / Serper / Mojeek become new table rows +
   small normalizers later, no rework. **Ruled out as future providers:**
   Google CSE (closing to new customers Jan 2027), Bing v7 (dead, HTTP 410),
   DuckDuckGo (no official API — scraping only, ToS-grey).
5. **Per-scan opt-in (privacy gate only)** — web tools are only *offered* to
   the model when the scan has web research enabled (default off); the Agent
   dock 🌐 toggle and the Settings → Search & research tab both control it.
   This toggle is **engine-agnostic** — it never selects or starts a search
   engine, it only permits web research for this scan (see decision 6).
6. **Search engines are Settings-configured, not dock-toggled** (owner
   revision, Aug 9 follow-up) — each search backend (bundled SearXNG, custom
   SearXNG-compatible instances, future Brave/Serper/Mojeek rows) carries an
   **Active/Inactive toggle** in Settings → Search & research, mirroring the
   model backends' enable switch. Rationale (owner): the engine the agent
   searches with is a Settings decision; wiring it to the dock 🌐 toggle
   would break the moment a second provider lands and the user isn't using
   SearXNG. The dock toggle (decision 5) and the Settings toggles are
   orthogonal layers.
7. **One Active search provider at a time (radio)** (owner decision, Aug 9
   follow-up) — enabling one provider disables all others, mirroring how the
   model picker clears other enabled-with-model backends so
   `pick_chat_backend` resolves deterministically. `web_search` returns ONE
   result set from ONE engine; concurrent actives would force merge/dedup
   complexity or arbitrary selection. The store keeps `enabled` + `order`
   per backend so a priority fallback chain (SearXNG down → Brave) is a
   resolver-only change later — no migration.

## Two layers: engine enablement vs per-scan opt-in

M7 separates two things the original draft conflated:

| Layer | Where | What it controls | Shape |
|---|---|---|---|
| **Engine** (global) | Settings → Search & research | *Which* search provider the agent uses | Per-backend **Active/Inactive** cards; **one Active at a time** (radio). Persisted in `search_backends.json`. |
| **Scan** (per-scan) | Dock 🌐 toggle (the only per-scan control since Aug 9 — a Settings copy was removed) | *Whether* the agent may leave the machine for this scan at all | `scans.web_research_enabled` (default off) — a privacy gate, engine-agnostic. The dock toggle is **disabled** until an engine is Active. |

A `web_search` tool call is offered only when **both** hold: the scan's
opt-in is on AND exactly one engine is Active. The dock toggle therefore
means "allow web research for this scan" — never "run SearXNG". When Brave
or Serper later become provider rows, the user flips the Active radio in
Settings and the dock toggle keeps meaning the same thing.

## The AGPL boundary (how MASA stays clean with SearXNG)

SearXNG is **AGPL-3.0** (verified from its LICENSE). Running it does not
infect MASA, because the copyleft never crosses the process boundary:

- AGPL §13 obligates the person who **modifies** the AGPL program and serves
  it over a network to offer the modified source. It does not reach into
  separate programs that merely communicate with the unmodified program.
- MASA never copies, imports, forks, or patches SearXNG code. It pulls the
  **unmodified upstream `searxng/searxng` image** as a separate container and
  calls its HTTP JSON API (`GET /search?q=…&format=json`). The JSON format is
  enabled via our own minimal `settings.yml` (a config artifact we author,
  not SearXNG code) mounted at `/etc/searxng/settings.yml`.
- Same discipline as the GPL/LGPL subprocess tools (Semgrep, ldid), and
  cleaner: SearXNG is a network peer, not even a subprocess import.
- What WOULD infect us (documented in `docs/licenses.md`): vendoring SearXNG
  code into the repo, `pip install searxng`, or running a modified/forked
  instance. None are in scope.
- Unchanged privacy reality: queries leave the machine (SearXNG proxies to
  public engines) — the "leaves the machine" boundary the M5 UI copy already
  states.

## Phase A — Search backend: provider registry + store (SearXNG only)

Mirror the M3/M5 BYOK architecture exactly — same shapes, smaller surface:

| Piece | Mirrors | Details |
|---|---|---|
| `search/providers.py` | `model/providers.py` | `SearchProvider` table: `id`, `name`, `kind` (`bundled`/`custom`), `base_url_required`, `key_required`, `key_env_var`, `query_style` (v1: `searxng`), `parse_style` (v1: `searxng`). Entries: `searxng` (bundled, default `http://localhost:8888`) + `custom` ("SearXNG-compatible instance", base URL only, no key — self-hosted or public instance) |
| `search/backends.py` | `model/backends.py` | `SearchBackend` dataclass mirrors `ModelBackend`: `id`, `provider_id`, `name`, `kind`, `base_url`, **`enabled`** (the Active/Inactive toggle), **`order`** (reserved for a future fallback chain — unused in v1), `api_key` for future keyed engines. `SearchStore`: JSON file `search_backends.json` in `data_dir` (perms `0600`), env-seeded from `MASA_SEARXNG_BASE_URL`, runtime-editable, `read`/`get`/`upsert`/`add`/`remove` + **`enable_only(id)`** (radio: enable one, disable all others, persist) + **`active()`** (the one enabled backend; `None` when all off) — the `BackendStore` semantics verbatim |
| `search/client.py` | `model/client.py` | `query(active_backend, q, ...)` → SearXNG `GET {base}/search?q=…&format=json` (json format must be enabled — our settings.yml), normalized to `[{title, url, snippet, engine}]`, bounded: per-call timeout (~20 s), top-N results (10), size caps |
| `config.py` | existing | `searxng_base_url` (`MASA_SEARXNG_BASE_URL`), `web_search_timeout_seconds`, `web_fetch_timeout_seconds`, `web_fetch_max_bytes` |

API surface (mirrors model backends): `GET/POST/DELETE /api/v1/search/backends`
+ `PUT /api/v1/search/backends/{id}` — bundled `searxng` deletable/editable,
`custom` add/remove. **`PUT {enabled: true}` triggers the radio semantics
server-side** (`enable_only`), so a raw API client can never leave two
providers Active at once; the Settings toggle is one UI over the same path.
The bundled `searxng` backend seeds **enabled** (mirroring local model
backends — it is the bundled default); the user can turn it off. `has_api_key`
honesty kept (only the SearXNG custom instance is keyless; future BYOK
engines carry keys).

## Phase B — On-demand web tools + two-layer gating

- **`web_search(query)`** — `search/client.py` against the **single Active
  backend** (`SearchStore.active()`); result rows with `url` + `snippet` so
  the model can cite source URLs.
- **`web_fetch(url)`** — httpx GET + **trafilatura** (pin **≥1.8.0** —
  Apache-2.0; earlier versions were GPLv3+) extraction → bounded
  agent-friendly article text (headline + paragraphs). Size + timeout caps;
  fetch is SSRF-guarded to http(s) only (it's an agent tool, so plain URL —
  no localhost redirect chains).
- **Gating (two gates, both must hold)** — migration **0008**:
  `scans.web_research_enabled` bool (default false) AND
  `SearchStore.active() is not None` (an Active engine exists).
  `web_search`/`web_fetch` are appended to `TOOL_SCHEMAS` only when both
  hold — same filter mechanism as `schemas_for_platform`
  (`_ANDROID_ONLY_TOOLS`), extended to a per-scan + store predicate. No
  Active engine → the dock 🌐 toggle is **disabled** (greyed, hint "enable a
  search engine in Settings"); scan enabled but the engine is unreachable →
  the tool errors with the Phase C compose hint. The system prompt tells the
  model when to search (current/external info: CVE lookups, MASTG guidance,
  dependency versions) and to cite URLs.
- **UI — two layers, engine-agnostic dock toggle** — the Agent dock 🌐 Web
  toggle goes live as the **per-scan opt-in ONLY** (PUTs
  `scans.web_research_enabled`; copy reads "Allow web research for this
  scan" — it never selects or starts an engine). It is **disabled** while no
  engine is Active (`SearchStore.active() is None`) — greyed with the hint
  "enable a search engine in Settings", mirroring the send button's
  no-model gate — and becomes toggleable only once an engine is Active.
  Settings → "Search & research" tab becomes live with the
  **search-backend list**: one card per provider (bundled SearXNG, custom
  instances, future rows) carrying an **Active/Inactive radio toggle**
  (enabling one disables the others) + base URL edit + **Test** probe,
  reusing the BackendsTab/BYOKTab card + chip patterns; plus a per-scan
  web-research section mirroring the dock toggle.

## Completion record (Aug 9, 2026 — e2e RUN + follow-ups)

**Containerized e2e — PASSED (Aug 9).** `docker compose --profile web up -d`
with the dev-only fake model (MASA_FAKE_MODEL=1 — Ollama off during dev).
What it uncovered and verified:

1. **SearXNG crashed on boot — a real bug in our bundled config.**
   `docker/searxng/settings.yml` was missing `use_default_settings: true`
   and a `server.secret_key`; SearXNG 2026.8.4 schema-validation hard-fails
   without them (`server.secret_key: The value has to be one of these
   types/values: str`). Fixed the file (fixed dev secret, localhost-only
   engine), validated in a throwaway container first, then recreated. This
   was the actual root cause of the earlier "Connection refused" — the
   service could never boot.
2. **Engine wiring verified live.** `POST /search/backends/searxng/test`
   from the app → `reachable: true, result_count: 1` (app→`searxng:8080`
   in-network; compose app/worker now set `MASA_SEARXNG_BASE_URL`). A
   persisted store keeps its own URL (the file is source of truth) —
   repointed via the documented Settings edit.
3. **Chat e2e — real web_search through compose SearXNG.**
   `PUT /scans/{id}/web-research {enabled:true}` → `POST …/chat/stream`
   → streamed thinking tokens, live `web_search` tool step (10 real results
   in ~1.1 s), `web_fetch` attempt → the top hit (medium.com) HTTP 403s the
   honest `MASA-agent/0.1` UA — degrades cleanly.
4. **Fake web script fixed (regression-tested).** It used to re-fetch the
   SAME failed URL until the 3-round limit, so the answer lost its
   citation; round 3 now composes from the search results (cites the top
   URL + "the top page blocked direct reading" note). Never retries a
   failed fetch.

**Follow-up — one-click engine start (owner).** Settings → Search &
research gained a **▶ Start engine** button on the bundled SearXNG card
whenever the probe reports it unreachable: `POST /search/backends/{id}/start`
runs the FIXED compose argv (no shell / no user input), compose file
discovered upward from cwd, then polls until the engine answers and returns
fresh health. 400 for custom instances; 502/504 carrying the manual command
when Docker is missing / times out. In-container (no Docker on the API
host) it degrades to the clean 502 with the manual command, never a raw
500.

**Follow-up — provider registry expanded (owner: "what about brave,
duckduckgo etc.? can it be simplified to base URL + API key?").** The
add-form is now a **provider picker** whose fields adapt per provider: base
URL (pre-filled with a per-provider default, optional when one exists) +
API key (required for keyed providers, hidden for SearXNG instances).
Providers: **custom** (SearXNG-compatible, base URL only), **brave**
(`X-Subscription-Token`, `GET /res/v1/web/search`), **serper**
(`X-API-KEY`, `POST /` JSON body), **mojeek** (`api_key` param,
`fmt=json`). `client.py` dispatches by `query_style` with per-style
normalizers + a key-rejected hint (401/403 → "check the API key in
Settings"); keyed engines env-seed from `MASA_BRAVE_API_KEY` etc. but stay
**disabled** (key presence never activates an engine — the radio does);
`GET /search/providers` is the picker's source of truth; `api_key` is
write-only in API responses (a "✓ key set" indicator on the card).
DuckDuckGo stays ruled out (no official API).

**Follow-up — manual web-search testing + chat chip overflow (owner).**
(1) The fake model now searches with the **user's own question text**
(`fake.py::_web_query` — last user message ≥4 chars, canned query as
fallback), so a manual test types its own search in the dock. Live-verified:
"SQLite database CVEs 2026" → `web_search {query: …}` → 10 results →
fetch sqlite.org/cves.html → cited answer. Manual recipe: fake model
selected + an Active engine in Settings + the dock 🌐 toggle on — then ask.
(2) **file:line citation chips could escape the chat bubble** — fixed
three ways: `shortenPath` in the dock (middle-ellipsis keeping the
filename:line tail; full path in the tooltip), `.src-chip`
`max-width:100%` + ellipsis floor, and `.md code`/`.msg`
`overflow-wrap: anywhere` (fenced code blocks keep their horizontal
scroll).

**Final gates:** **459 backend tests green + ruff clean; `tsc -b` + `vite
build` green**; app image rebuilt and healthy in compose. Remaining owner
checkpoint (not a blocker, consistent with M4–M6): **real-model QA** — a
web-research chat with a real LLM (Ollama) to see the model trigger
tools on its own.
