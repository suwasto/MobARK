# M8 — Edit & Recompile (Android): Plan + Progress

Written Aug 10, 2026 · **STATUS: PLANNED (kickoff spec complete — no code
written).** Implementation contract for M8: five phases (A–E) — toolchain +
on-demand apktool decode · edits model + Smali view · rebuild pipeline +
resign · agent edit flow · hardening + contract-style e2e. Owner decisions
locked at the Aug 10, 2026 kickoff interview — see below. Full interview
record, architecture, and edge cases live in
[`docs/m8-kickoff-spec.md`](../m8-kickoff-spec.md) (this doc is the
milestone tracker; the spec is the source of truth for the plan).

## The kickoff (owner interview, Aug 10, 2026)

The M8 task list (see `docs/masa-tasks.md`) was taken as the starting
contract, then the owner was interviewed across three rounds (scope +
pipeline architecture; editing UX + agent flow; rebuild/signing/iOS/e2e) to
resolve every non-obvious decision before any code. Two questions surfaced
genuinely load-bearing reframes:

1. **When does apktool decode run?** A full decode of a large APK takes
   ~30 s–2 min and adds real disk to the scan's working dir. The owner chose
   **on-demand, first Smali view** — the scan pipeline stays untouched; the
   decode job runs only when the user first switches to the Smali view (or
   starts an edit), then caches.
2. **Is iOS edit/recompile actually shippable?** The owner correctly probed
   the sideloading reality before scoping: research confirmed that `ldid -S`
   fake-signed IPAs **only install on jailbroken devices (AppSync Unified)**,
   are rejected by stock iOS, and won't run in the simulator (wrong platform
   slice). The honest iOS deliverable would be a handoff artifact for the
   user's own Sideloadly/Apple-ID signing — the owner judged that **not worth
   M8 scope**, deferring iOS edits to v1.1 (§"Why iOS is deferred" below).

## Owner decisions (locked Aug 10, 2026)

1. **Smali decode is on-demand** — the apktool disassemble runs as an RQ
   job the first time the user opens the Smali view (or starts an edit), not
   as part of the scan pipeline. UI shows a spinner + retry; decode is cached
   per scan. The M5 "Smali arrives in M8" placeholder chip becomes the
   trigger.
2. **Edits are diffs in the DB, applied at rebuild** — an `edits` table is
   the source of truth (original + new content + unified diff per edit row);
   the on-disk apktool tree stays the pristine baseline; the rebuild job
   overlays applied edits onto a fresh copy of the decoded tree. Reproducible,
   revert-safe, attribution-friendly (vs. mutating the working tree directly).
3. **Android only; iOS edit/recompile deferred to v1.1** — the architecture
   keeps a clean seam for iOS later (edits table + artifact pipeline +
   resign step are platform-shaped already), but M8 ships no iOS editing.
   iOS keeps today's read-only bundle view.
4. **M8 toolchain bundled into the image; the 350–450 MB gate is bumped** —
   apktool (pinned official jar) + Android build-tools `zipalign`/`apksigner`
   (pinned download) are installed at build time; `keytool` already ships
   inside the bundled JRE. Owner explicitly approved growing past 450 MB if
   needed — M8 is a flagship feature, not a guideline case.
5. **iOS deferral rationale** — see the dedicated section below; the
   sideloading research (ldid/AppSync/simulator) was verified live before
   the decision.
6. **Agent surface = dock chat tool AND the mockup's inline "Ask agent to
   edit" bar** — `propose_smali_edit` joins the tool loop in the dock, and
   the Decompiler toolbar gains the mockup-faithful inline bar that sends an
   instruction with the currently-open file pre-set.
7. **Diff review = unified diff, file-by-file apply** — one agent proposal
   may span several files, but the human accepts/rejects each file's diff
   individually. Apply/Reject/Revert are human API calls, never agent tools.
8. **Full edit/build history per scan** — per-file "Restore original" plus a
   per-scan "Edits & builds" list: every build row (status, stage, error,
   timestamp, edits included) and re-download of any prior artifact.
9. **Contract-style e2e (no emulator/device)** — automated validation
   asserts pipeline success + artifact integrity: `apksigner verify` passes,
   zipalign correct, signature fingerprint **differs from the original APK**,
   filename carries the resigned label. "Installs and runs on a real device"
   is an owner manual checkpoint, not an automated gate.
10. **One install-scoped test keystore** — generated on first rebuild into
    `data_dir` (`masa-test.jks`, alias `masa`, plaintext storepass at `0600`
    per the BYOK-key precedent) and reused for every scan/build — a stable
    test signature, standard apktool practice.

## Why iOS edit/recompile is deferred (the research behind decision 5)

Verified Aug 10, 2026 (web research) — this is the reality the owner probed
and why M8 ships Android-only:

| Path to run a modified IPA | Reality |
|---|---|
| **`ldid -S` fake signature → stock (non-jailbroken) device** | **Will not install or run.** iOS requires a signature bound to a valid provisioning profile/Apple-issued cert; ad-hoc fake signatures are rejected by the kernel/installd. |
| **`ldid -S` → jailbroken device with AppSync Unified** | Installs and runs (AppSync bypasses signature checks) — the only "works out of the box" path, and it depends on a jailbroken device. |
| **iOS Simulator** | Won't run an iOS-platform-slice binary even when `ldid`-signed — wrong platform, needs Mach-O patching (out of scope). |
| **Non-jailbroken device via the user's own signing** | Possible but the user must re-sign with their own credentials: Sideloadly/AltStore (free Apple ID — 7-day expiry, 3-app limit, Developer Mode) or a $99/yr account + UDID registration. MASA's output would only be a *handoff input* for that workflow. |

Conclusion: an iOS "resign" feature in M8 would ship an artifact that needs
either a jailbroken device or external tooling to be useful — a poor fit for
M8's polish budget. Deferred to v1.1 with the plist/entitlement/resource
edit + `ldid` resign path preserved in the PRD's v1 scope line. `ldid` is
**not** installed in the image; the `docs/licenses.md` "future M8 tools"
note stays accurate.

## The pipeline at a glance (full detail in the spec §5)

On-demand decode (`run_apktool_decode`) → apktool tree exposed as editable
roots (`smali{,classesN}/`, `res/`, decoded `AndroidManifest.xml`) alongside
the read-only jadx `sources/` root → manual edits (`POST /edits`) or agent
proposals (`propose_smali_edit`) stored as DB diffs → human applies/rejects →
`run_rebuild`: overlay applied edits on a fresh copy → `apktool b` →
`zipalign -f` → `apksigner sign` with the install-scoped keystore →
`apksigner verify` sanity gate → downloadable `…-resigned-test-….apk`. Every
step is a bounded subprocess call with a specific error; the DB (`edits`,
`builds`, `scans.apktool_status`, migration 0009) is the source of truth;
one rebuild at a time per scan.

- [ ] Migration 0009: `scans.apktool_status` (`not_started|queued|decoding|ready|failed`) + `scans.apktool_error` (text) — decode state filesystem-derived like the graph (`<work>/<scan>/apktool/AndroidManifest.xml` exists = ready) with the status column for in-flight states; one decode per scan (cached, no re-decode in v1)
- [ ] `run_apktool_decode` RQ job + `POST /scans/{id}/smali` (202 enqueue; 409 while decoding/ready) + `GET /scans/{id}/smali-status` (or folded into the scan read)
- [ ] Frontend: the Decompiler toolbar **Smali chip goes live** — `not_started` → click POSTs + polls status (spinner in-chip); `failed` → disabled with the specific reason + retry; `ready` → active
- [ ] Unit tests (mocked subprocess, no network): wrapper argv/error-mapping/timeout; status transitions; trigger API 409s; migration 0009 up/down

## Phase B — Edits model + Smali view

- [ ] Migration 0009 (extended): **`edits`** table — `id`, `scan_id` FK, `file_path` (apktool-root-relative), `original_content`, `new_content` (full files), `unified_diff` (generated), `source` (`manual|agent`), `instruction` (nullable — agent attribution), `status` (`proposed|applied|rejected|reverted`), `build_id` FK (nullable), `created_at`, `applied_at`
- [ ] Editability predicate `can_edit(scan, path)`: only `smali*/`, `res/`, and the decoded `AndroidManifest.xml`; jadx `sources/`, `original/`, `unknown/`, and the whole iOS bundle always read-only — enforced **server-side** in the edit API, the rebuild apply step, and (defensively) the agent tool, not just in the UI
- [ ] Edit CRUD API: `GET /scans/{id}/edits` · `POST /scans/{id}/edits` (manual `{file_path, content}`; decode-ready + editability + size-cap guards) · `GET /scans/{id}/edits/{eid}/diff` (unified diff) · `POST …/apply|reject|revert`
- [ ] Same-file stacking: a new edit baselines on the prior applied edit's effective content; revert pops to the previous state; the diff is regenerated per state
- [ ] Effective-content reads: the viewer returns baseline + newest applied edit's `new_content` for the open path; restore-original returns the baseline
- [ ] File tree: `list_tree` appends the apktool roots once decoded — `smali`, `smali_classes2…N`, `res`, decoded `AndroidManifest.xml` (synthetic root) — reusing the bounded walk + traversal guards; nothing changes until `apktool_status == ready`
- [ ] Java⇄Smali mapping: open jadx `sources/.../Foo.java` → `smali{,classesN}/.../Foo.smali` (multidex-aware search, first-found wins) and back; jadx's own fallback `.smali` files inside `sources/` stay read-only — only the apktool smali is editable, and the UI must not confuse the two
- [ ] Frontend edit mode: editable paths swap the read-only highlighted viewer for a plaintext editor (textarea + line numbers — no new editor dependency; hljs lacks a smali grammar), dirty indicator, Ctrl/Cmd+S → `POST /edits`; non-editable paths keep the mockup read-only hint + disabled affordances
- [ ] Unit tests: predicate matrix; edit CRUD + diff generation + stacking + transitions; effective-content overlay; tree roots; Java⇄Smali mapping incl. multidex + not-found

## Phase C — Rebuild pipeline + resign

- [ ] Migration 0009 (extended): **`builds`** table — `id`, `scan_id` FK, `status` (`queued|running|done|failed`), `stage` (`applying|rebuilding|zipping|signing|done`), `error` (text), `edits_json` (snapshot of applied edit ids), `artifact_name`, `artifact_path`, `artifact_sha256`, `created_at`, `finished_at`
- [ ] `run_rebuild` RQ job — stages, each a bounded subprocess call with a specific failure: **(1) applying** copy the decoded tree per build + overlay `applied` edits · **(2) rebuilding** `apktool b <dir> -o <unsigned.apk>` · **(3) zipping** `zipalign -f 4` (**before** signing — v2+ preserves alignment) · **(4) signing** `apksigner sign --ks …` (v1/v2/v3 defaults) · **(5) sanity** `apksigner verify` must pass
- [ ] Stage-failure semantics: any failure → `builds.stage` + `builds.error` with the stderr excerpt, `status=failed`, **no artifact written**; a post-build verify failure is `failed` too — never a silently broken APK
- [ ] Install-scoped test keystore (one per MASA install, decision 10): `keytool -genkeypair -keystore <data_dir>/masa-test.jks -alias masa -keyalg RSA -keysize 2048 -validity 10000` on first rebuild; reused everywhere; plaintext storepass in `data_dir` at `0600` (BYOK-key precedent, documented honestly)
- [ ] Artifact naming + labeling: `{original}-resigned-test-{scan_id}-b{n}.apk` under `data_dir/artifacts/<scan_id>/`; the resigned label is **embedded in the output filename** (task-list requirement)
- [ ] API: `POST /scans/{id}/rebuild` (409 while a build is running; 400 decode-not-ready; zero-edit rebuild allowed — open item 4) · `GET /scans/{id}/builds` · `GET /scans/{id}/builds/{bid}/download` (`Content-Disposition` with the labeled name)
- [ ] Frontend recompile modal (mockup-faithful): **persistent, un-dismissable "resigned test build" warning**, live pipeline stages (polling), done → Download, failed → specific error + log excerpt
- [ ] "Edits & builds" full-history panel (decision 8): per-file restore-original; build list with per-build status/stage/error/edits; re-download any prior artifact
- [ ] Unit tests (mocked subprocess): apply-overlay; stage order (zipalign before apksigner asserted); keystore single-creation + reuse; artifact naming; each stage's failure path; verify gate; API 409/400; builds list + download filename

## Phase D — Agent edit flow

- [ ] `propose_smali_edit(file, instruction, new_content)` in `agent/tools.py` — Android-only (`_ANDROID_ONLY_TOOLS`) **and** gated on `apktool_status == ready` (else a clean "open the Smali view first" error); validates editability + content size; stores a `proposed` edit row + generated unified diff; **never auto-applies**; returns `{edit_id, file, instruction, diff}`. (The `(file, instruction)` task-list signature gains `new_content` — the model composes the full edited file after `read_file`, so the tool can produce a byte-exact diff; flagged as kickoff checkpoint, open item 3)
- [ ] Apply/Reject/Revert stay human API calls — not agent tools (decision 7)
- [ ] Multi-file proposals: one natural-language request may touch several files; the review panel lists them file-by-file with per-file Apply/Reject
- [ ] Fake model (M6.1) edit-demo script: read_file → propose_smali_edit → cited diff — the flagship flow demos with zero Ollama and powers the containerized e2e (M7 precedent)
- [ ] Frontend diff review panel: unified diff per file with Apply/Reject; multi-file proposals reviewed file-by-file
- [ ] Inline **"Ask agent to edit" bar** in the Decompiler toolbar (mockup-faithful, decision 6): visible when an editable file is open + a chat model is connected; sends the instruction with the open file pre-set
- [ ] Dock chat: the tool is offered in the normal tool loop, including `chat/stream` SSE (`tool_start`/`tool_end` frames + `tool_runs` trace)
- [ ] Tests: gating matrix (platform, decode status, non-editable path); proposed-not-applied; diff shape; size cap; fake-model flagship (read → propose → diff → apply → rebuild); multi-file proposal

## Phase E — Hardening + contract-style e2e

- [ ] **Fail-loudly awkward-APK test**: pin ≥1 APK known to trip apktool (resource clashes / edge-case bytecode — candidate chosen at kickoff, open item 2); assert a specific stage error, no artifact produced, build row `failed`

- [ ] Gates: backend pytest + ruff; `tsc -b` + `vite build`; image rebuild + size measurement recorded (bump approved); browser DOM check of the live toggle/edit/recompile UI (recurring chrome-devtools outage covered by code review, per project precedent)
