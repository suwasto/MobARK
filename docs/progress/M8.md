## The kickoff (owner interview, Aug 10, 2026)

The M8 task list (see `docs/masa-tasks.md`) was taken as the starting
contract, then the owner was interviewed across three rounds (scope +
pipeline architecture; editing UX + agent flow; rebuild/signing/iOS/e2e) to
resolve every non-obvious decision before any code. Two questions surfaced
genuinely load-bearing reframes:

1. **When does apktool decode run?** A full decode of a large APK takes
   ~30 s–2 min and adds real disk to the scan's working dir. The owner chose
   **on-demand, first Smali view** — the scan pipeline stays untouched; the
   decode job runs only when the user first switches to the Smali view (or
   starts an edit), then caches.
2. **Is iOS edit/recompile actually shippable?** The owner correctly probed
   the sideloading reality before scoping: research confirmed that `ldid -S`
   fake-signed IPAs **only install on jailbroken devices (AppSync Unified)**,
   are rejected by stock iOS, and won't run in the simulator (wrong platform
   slice). The honest iOS deliverable would be a handoff artifact for the
   user's own Sideloadly/Apple-ID signing — the owner judged that **not worth
   M8 scope**, deferring iOS edits to v1.1 (§"Why iOS is deferred" below).

## Owner decisions (locked Aug 10, 2026)

1. **Smali decode is on-demand** — the apktool disassemble runs as an RQ
   job the first time the user opens the Smali view (or starts an edit), not
   as part of the scan pipeline. UI shows a spinner + retry; decode is cached
   per scan. The M5 "Smali arrives in M8" placeholder chip becomes the
   trigger.
2. **Edits are diffs in the DB, applied at rebuild** — an `edits` table is
   the source of truth (original + new content + unified diff per edit row);
   the on-disk apktool tree stays the pristine baseline; the rebuild job
   overlays applied edits onto a fresh copy of the decoded tree. Reproducible,
   revert-safe, attribution-friendly (vs. mutating the working tree directly).
3. **Android only; iOS edit/recompile deferred to v1.1** — the architecture
   keeps a clean seam for iOS later (edits table + artifact pipeline +
   resign step are platform-shaped already), but M8 ships no iOS editing.
   iOS keeps today's read-only bundle view.
4. **M8 toolchain bundled into the image; the 350–450 MB gate is bumped** —
   apktool (pinned official jar) + Android build-tools `zipalign`/`apksigner`
   (pinned download) are installed at build time; `keytool` already ships
   inside the bundled JRE. Owner explicitly approved growing past 450 MB if
   needed — M8 is a flagship feature, not a guideline case.
5. **iOS deferral rationale** — see the dedicated section below; the
   sideloading research (ldid/AppSync/simulator) was verified live before
   the decision.
6. **Agent surface = dock chat tool AND the mockup's inline "Ask agent to
   edit" bar** — `propose_smali_edit` joins the tool loop in the dock, and
   the Decompiler toolbar gains the mockup-faithful inline bar that sends an
   instruction with the currently-open file pre-set.
7. **Diff review = unified diff, file-by-file apply** — one agent proposal
   may span several files, but the human accepts/rejects each file's diff
   individually. Apply/Reject/Revert are human API calls, never agent tools.
8. **Full edit/build history per scan** — per-file "Restore original" plus a
   per-scan "Edits & builds" list: every build row (status, stage, error,
   timestamp, edits included) and re-download of any prior artifact.
9. **Contract-style e2e (no emulator/device)** — automated validation
   asserts pipeline success + artifact integrity: `apksigner verify` passes,
   zipalign correct, signature fingerprint **differs from the original APK**,
   filename carries the resigned label. "Installs and runs on a real device"
   is an owner manual checkpoint, not an automated gate.
10. **One install-scoped test keystore** — generated on first rebuild into
    `data_dir` (`masa-test.jks`, alias `masa`, plaintext storepass at `0600`
    per the BYOK-key precedent) and reused for every scan/build — a stable
    test signature, standard apktool practice.

## Why iOS edit/recompile is deferred (the research behind decision 5)

Verified Aug 10, 2026 (web research) — this is the reality the owner probed
and why M8 ships Android-only:

| Path to run a modified IPA | Reality |
|---|---|
| **`ldid -S` fake signature → stock (non-jailbroken) device** | **Will not install or run.** iOS requires a signature bound to a valid provisioning profile/Apple-issued cert; ad-hoc fake signatures are rejected by the kernel/installd. |
| **`ldid -S` → jailbroken device with AppSync Unified** | Installs and runs (AppSync bypasses signature checks) — the only "works out of the box" path, and it depends on a jailbroken device. |
| **iOS Simulator** | Won't run an iOS-platform-slice binary even when `ldid`-signed — wrong platform, needs Mach-O patching (out of scope). |
| **Non-jailbroken device via the user's own signing** | Possible but the user must re-sign with their own credentials: Sideloadly/AltStore (free Apple ID — 7-day expiry, 3-app limit, Developer Mode) or a $99/yr account + UDID registration. MASA's output would only be a *handoff input* for that workflow. |

Conclusion: an iOS "resign" feature in M8 would ship an artifact that needs
either a jailbroken device or external tooling to be useful — a poor fit for
M8's polish budget. Deferred to v1.1 with the plist/entitlement/resource
edit + `ldid` resign path preserved in the PRD's v1 scope line. `ldid` is
**not** installed in the image; the `docs/licenses.md` "future M8 tools"
note stays accurate.

## The pipeline at a glance (full detail in the spec §5)

On-demand decode (`run_apktool_decode`) → apktool tree exposed as editable
roots (`smali{,classesN}/`, `res/`, decoded `AndroidManifest.xml`) alongside
the read-only jadx `sources/` root → manual edits (`POST /edits`) or agent
proposals (`propose_smali_edit`) stored as DB diffs → human applies/rejects →
`run_rebuild`: overlay applied edits on a fresh copy → `apktool b` →
`zipalign -f` → `apksigner sign` with the install-scoped keystore →
`apksigner verify` sanity gate → downloadable `…-resigned-test-….apk`. Every
step is a bounded subprocess call with a specific error; the DB (`edits`,
`builds`, `scans.apktool_status`, migration 0009) is the source of truth;
one rebuild at a time per scan.
